[Sun][P1] Backend skeleton up: FastAPI + one sequential worker thread + job.json after every item status change. Mock job with 2 photos runs start to finish via curl.
[Sun][P1] Real-ESRGAN ncnn-vulkan (20220424 Windows build) runs on an Intel UHD 620 iGPU via Vulkan, no CUDA. Gotcha: `-h` prints usage but exits with code 127, so the health check looks for the usage text instead of a zero exit code.
[Sun][P1] Gotcha: the binary can exit 0 without writing an output file (e.g. GPU out of memory), so we check the output file exists, not just the exit code, before retrying with `-t 128`.
[Sun][P1] Upscale timings, Intel UHD 620 iGPU, realesrgan-x4plus at 4x: 220px → 38s, 256px → 39s, 800x800 → 198s. 2x of 220px (4x then halve) → 23s. That's roughly 20s fixed start-up per photo + ~0.3 megapixels/min.
[Sun][P1] A 2800x2100 scan (shrunk to 2500x1875 by the input guard) at 4x did NOT finish within 15 min on the iGPU, so it timed out. Fixes: timeout raised to 30 min, and a timeout no longer retries with -t 128 (smaller tiles don't make a slow GPU faster, they just double the wait). Open question for Phase 4: lower the 2500px guard or default to 2x on weak laptops.
[Sun][P2] UI is plain HTML/JS: the before/after slider uses a clip-path'd 'before' image over the 'after' image, driven by pointer events, so mouse, touch and arrow keys all work with no library. Folder drops needed webkitGetAsEntry read synchronously inside the drop event, since entries go stale after the first await.
[Sun][P2] Album zip is one offline album.html (inline CSS/JS, relative image paths) plus photos/, originals/, captions.json. Captions are HTML-escaped and print CSS gives one photo per page. Tested: no network requests beyond file://, and a 3-photo album prints as 3 pages.
[Sun 21:39][P3] Gemma captions are real: stdlib urllib to Ollama on localhost only (any non-local OLLAMA_HOST is refused), photo shrunk to 1024px JPEG, Ollama's `format` set to a JSON schema {caption, decade} so we always get parseable JSON. gemma4 is a "thinking" model, so we pass `think: false`, otherwise it reasons before answering and each caption is slower.
[Sun 21:39][P3] Gemma 4 E4B (gemma4:e4b-it-qat) on 8 public-domain photos: ~5s/photo warm, ~12s for the first one (model load). Prompt tuning once ("write it like a kind relative labelling an album, not a security camera" + photo-era hints) made it name the occasion: "A bride and two young women pose together in a formal studio setting, holding large bouquets." (was "Three women pose together in formal attire").
[Sun 21:39][P3] Gemma 4 E2B vs E4B, same 8 photos: E2B ~4.9s vs ~5.1s/photo, so barely faster on this machine, but noticeably worse: it called every group "a family" despite the prompt saying not to invent relationships, and turned three bridesmaids into "a family of four". E4B stays the default; E2B is only the fallback for a low-RAM laptop (6.1GB vs 4.3GB on disk).
[Sun 21:39][P3] Decade guesses are the weak spot. E4B said 1930s for a 1902 school photo and 1960s for a 1925 wedding; E2B was actually closer on the oldest photos (1900s, 1910s). Present the decade as "Gemma's guess", never as a fact.
